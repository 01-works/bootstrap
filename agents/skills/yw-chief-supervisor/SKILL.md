# YW Chief Supervisor

여러 감독 세션의 운영을 감사하고 현황을 사용자에게 보고하며, 완료된 세션의 수명주기를 마무리한다. **총괄 감독은 직접 구현하지 않고, 진행 중인 다른 감독의 lane을 인수·중단·정리하지 않는다.** 완료가 확인된 세션만 아래 정리 조건에 따라 닫는다. 작업자에게 직접 지시하지 않고 소유 감독에게 `send_agent_prompt`로 전달한다. 감독이 응답 불가하면 사용자에게 묻는다. 스킬 수정처럼 새 작업이 필요하면 [yw-supervisor](../yw-supervisor/SKILL.md) 방식으로 자신의 작업자를 배정하고, 아래 소유 기록에 남긴다.

이 스킬·관련 프로필 notes·`agents/paseo.md` 절도 [yw-supervisor 첫머리의 변경 창구 규칙](../yw-supervisor/SKILL.md)을 따른다. 변경 PR은 총괄 감독 lane으로 모으고 다른 세션은 bootstrap 이슈로 제안한다([#64](https://github.com/01-works/bootstrap/issues/64)).

## 시작과 기록

- 사용 가능한 `paseo` 스킬과 [yw-supervisor](../yw-supervisor/SKILL.md)를 읽는다. 도구 사용·작업 배정·공유 기록·소유권의 일반 규칙은 그 문서를 따른다. 프로필 선택은 bootstrap 저장소 `agents/paseo.md`의 "프로필"·"총괄 운영 스킬", 자원 운영은 bootstrap 저장소 `agents/heavy-queue.md`를 따른다.
- 사용자가 맡긴 감사 대상과 범위를 기록한다. 발견한 감독·lane을 감사 목록에 넣는 것은 소유권 인수가 아니다. 공유 기록이 원장이며, 도구에 보이지 않는 것을 정체·종료의 증거로 쓰지 않는다.
- 로컬 기록은 `${XDG_STATE_HOME:-$HOME/.local/state}/yw-supervisor/<총괄 감독 세션 ID>-chief/tasks.md`에 두고 상태 전이 때 갱신한다. 감독↔lane 매핑, 지적(확인/가설과 근거 출처), 독립 검토·합의 결과, 감독에게 보낸 조치, 사용자 결정 대기와 다음 조치, 완료 판정 근거·교차 모델 확인, 정리한 것·남긴 것과 이유를 남긴다. 경로를 보고와 인계에 포함하고 제품 저장소에는 커밋하지 않는다. 기록을 쓸 수 없으면 대화에 유지하고 지속성 한계를 알린다.
- 총괄 감독이 직접 배정한 작업은 감사 기록과 따로 `${XDG_STATE_HOME:-$HOME/.local/state}/yw-supervisor/<총괄 감독 세션 ID>/tasks.md`에 yw-supervisor 형식(`감독:` 머리말 포함)으로 기록한다. 이 소유 기록은 다른 총괄 감독의 발견 스캔에 포함되어 소유 근거가 된다. `-chief` 감사 기록에는 그 작업의 소유 근거를 쓰지 않는다.

## 감독과 lane 발견

- `list_hosts`로 등록된 호스트를 확인한다. 호스트별 `serverId`를 명시해 `list_workspaces(includeBackground: true)`를 호출한 뒤, **workspace마다 `cwd`를 지정해 `list_agents(cwd, includeBackground: true, limit: 200)`**를 호출한다. 결과의 `labels`에서 `yw.role=supervisor`인 후보를 먼저 찾고, 라벨이 없는 기존 감독은 아래 소유 기록·부모 관계·heavy 정보로 보완한다. `list_agents`를 cwd 없이 부르면 호출자 workspace 쪽 에이전트만 보일 수 있고, 상한에 닿은 결과도 전체 목록으로 간주하지 않는다. 개별 상태 조회는 발견된 후보와 실제 판정 대상에 쓴다. `{serverId, agentId}`는 함께 기록한다.
- 작업자→감독 매핑은 다음 세 출처를 대조한다. 라벨 `paseo.parent-agent-id`, 해당 호스트의 `${XDG_STATE_HOME:-$HOME/.local/state}/yw-supervisor/*/tasks.md`에 있는 `감독:` 머리말과 작업 기록, `yw-heavy status`의 감독자 정보다. 기록을 스캔할 때 `*-chief` 디렉터리는 제외한다. 총괄 감독의 감사 매핑 표는 소유 기록이 아니며, 총괄 감독이 직접 배정한 작업은 `-chief`가 없는 소유 기록으로 찾는다. `감독:` 머리말이 없는 기존 기록은 그 출처로 소유를 확인할 수 없다고 남긴다. 부모 라벨은 부모 보관으로 빠질 수 있고, 역할 라벨의 인계 복사를 전제하지 않는다. `yw-heavy status`는 round-robin 모드에서 감독자 순환 목록을, compat 모드에서는 각 대기 줄의 supervisor 값을 대조한다. heavy 정보는 현재 제출자만 보여 줄 수 있으므로 어느 한 출처도 전체 감독 목록으로 보지 않는다.
- 감독 ID, lane의 프로젝트·호스트·workspace·cwd·브랜치·이슈/PR, 담당 작업자·리뷰어 ID, 기록상/실제 상태, 다음 조치와 확인 시각·출처를 매핑한다. 접근할 수 없는 다른 기기의 로컬 기록은 공유 이슈·PR과 소유 감독의 설명으로 보완하고, 확인 불가는 그대로 남긴다. 기록과 라벨이 충돌하면 임의로 소유자를 정하지 않고 소유 감독에게 확인을 요청하며, 해결되지 않으면 사용자에게 묻는다.
- 판정이나 전송 전에 감독 상태를 확인한다. closed·error면 [yw-supervisor의 "진행과 검증"](../yw-supervisor/SKILL.md#진행과-검증)의 **이어받은 작업자** 절차(`zerosub.continued-from`·`handoff.from`)를 감독에게 적용해 끝까지 이어진 최신 감독을 대상으로 하고 매핑을 갱신한다. 옛 closed·error 세션에는 보내지 않는다. 후속 감독이 없음을 확인했을 때만 응답 불가로 보고하며, 후속 소유를 확인할 수 없으면 판단 불가로 남긴다.

## 감사 체크리스트

대상 저장소의 지침·runbook·이슈·PR을 먼저 읽고 그 저장소 기준을 적용한다. 리뷰 단계나 반복 상한을 새로 만들어 강요하지 않는다.

| 항목 | 확인할 것 |
|---|---|
| 기록과 실제 상태 | 감독 기록상 실행 중인 리뷰어·작업자가 실제로 존재하는지, 저장된 ID가 `not found`인지, 인계·세션 전환 기록과 맞는지 |
| 정체와 보고 경로 | 감독·작업자가 모두 idle인데 다음 조치가 없는 lane, 백그라운드 대기에 결과를 소유 감독에게 직접 보고할 경로가 있는지 |
| 저장소 정책 | 리뷰 독립성·tier별 리뷰 요건·자동 fix/review 반복 상한, `--no-verify` 훅 우회, triage 전 구현, 이슈 claim·라벨·PR 증거의 동기화가 대상 저장소 규칙과 맞는지 |
| 자원 | heavy 대기열 사용과 감독자 전체 Paseo agent ID, OOM·메모리 문제와 모델 한도에 따른 대체·인계 기록이 운영 규칙과 맞는지 |
| 파괴적 조작 안전 | archive·정리 전에 대상 cwd와 호출자 자신의 workspace cwd를 대조해 자기 workspace가 아닌지 확인했는지 |
| 소유자 없는 lane | 오래된 PR·worktree·stash의 담당 감독이 확인되는지. 소유자가 없으면 목록화만 하고 정리는 사용자 승인 뒤 소유·실행 담당을 정해 맡긴다 |

heavy의 모드별 한도·전환·이전 ID 이행·회수 기준은 bootstrap 저장소 `agents/heavy-queue.md`와 [yw-supervisor](../yw-supervisor/SKILL.md)를 적용한다. 총괄 감독이 다른 감독의 대기 줄·잠금·프로세스를 직접 정리하지 않는다.

## 독립 검토와 조치

### 판단 범위

오판의 영향, 되돌리기 어려움, 해석의 불확실성을 기준으로 총괄 혼자 처리할 일과 교차 모델 합의가 필요한 판단을 구분한다.

| 처리 방식 | 업무·판단 | 아래 모델 구성 표의 열 |
|---|---|---|
| 총괄 단독 | 상태·PR·로그 조회, 사실 목록과 기록 갱신, 근거 요청 | 해당 없음 |
| 총괄 단독 | 기존 결정 전달, 완료 조치의 readback, 이미 합의한 조치의 진행 확인 | 해당 없음 |
| 총괄 단독 | 실행을 수반하지 않는 잠정 가설 보고 | 해당 없음 |
| 교차 모델 합의 | 정책 위반·중대 결함의 확정 또는 기각 | 중요한 감사·완료 판단 |
| 교차 모델 합의 | 누적 사용자 목표의 완료 판정과 세션·workspace 정리 | 중요한 감사·완료 판단 |
| 교차 모델 합의 | 소유권 충돌, 사용자 승인 범위·기존 규칙의 예외 판단 | 중요한 감사·완료 판단 |
| 교차 모델 합의 | 여러 lane에 영향을 주는 운영 규칙·우선순위 변경의 확정 | 중요한 감사·완료 판단 |
| 교차 모델 합의 | 여러 lane에 영향을 주는 새 운영 규칙·우선순위 정책의 설계 | 새 운영 정책 설계 |

합의는 실행 권한을 추가하지 않는다. 사용자 승인이 필요한 조치는 아래 "조치 전달과 확인"의 승인 조건을 따른다.

### 모델 구성

- `list_profiles`의 모든 notes를 읽고 **총괄 감독과 다른 모델 계열의 읽기 전용 독립 검토자**를 고른다. 사용자가 모델을 지정하면 그 지정이 우선한다.

| 총괄 감독 | 중요한 감사·완료 판단 | 새 운영 정책 설계 |
|---|---|---|
| Opus | Deep Reviewer (Astra) | Architect (Astra) |
| Astra(인계) | Deep Reviewer (Opus) | Architect (Opus) |

- 총괄을 포함한 기본 2모델이면 충분하다. 매번 3자 위원회를 만들지 않는다. Opus 총괄은 Opus 가용 여부와 관계없이 위 교차 모델 설계·독립 검토에 Astra를 쓴다. 이는 Supervisor (Astra)의 총괄 인계 조건과 별개다.
- 위 교차 모델 합의 범위에서는 이 스킬의 모델 구성이 notes보다 우선한다.
- Reviewer(Sol)는 상태·SHA·로그·명세 대조, 테스트 근거 확인, 좁은 결함 검토에 쓴다. 중요한 결함도 발견할 수 있으므로 단순 자료 수집으로 한정하지 않지만, 그 결과를 Opus↔Astra 합의와 동등하다고 기록하지 않는다.
- 상대 모델을 쓸 수 없으면 중요한 판단은 미합의로 보존해 보고하거나, 사용자가 지정한 대체 구성을 쓴다. 같은 모델 계열의 새 세션만으로 교차 모델 검토를 충족했다고 보지 않는다.
- 총괄 자신의 bootstrap PR 같은 코드 리뷰는 [yw-supervisor의 "진행과 검증"](../yw-supervisor/SKILL.md#진행과-검증)에 있는 기존 흐름(Reviewer Sol + 필요 시 Deep Reviewer)을 따른다.

### 독립 판정과 불일치 처리

1. 검토자에게 감사 범위, 대상 저장소 지침, 감독 기록·실제 상태·공유 기록의 원자료와 출처를 먼저 전달한다. **검토자가 원자료로 독립 판정을 쓴 뒤에** 총괄의 가설·조치안을 전달해 반례·빠진 맥락·부작용을 반박하게 한다. 읽기 전용이며 직접 수정하거나 다른 감독·작업자에게 지시하지 말라고 명시한다. 권한 모드 이름만으로 읽기 전용이 강제된다고 가정하지 않는다.
2. 불일치를 `사실 오류 / 정책 해석 / 사용자 선호·권한 / 증거 부족`으로 분류한다.
3. 필요한 원자료를 추가 확인하고 바뀐 쟁점만 한 차례 재검토한다. 사실 쟁점은 Sol로 확인할 수 있다. 새 근거 없이 검토를 반복하지 않는다.
4. 그래도 합의되지 않으면 양쪽 근거를 기록한다. 증거 부족은 판단 불가로 남기고, 사용자 선호·권한 문제는 사용자 결정으로 올린다. 그 밖의 미합의 판단도 근거와 함께 결정 요청으로 보고한다. 영향을 받는 조치만 보류하며 다수결이나 반복 설득으로 승인을 만들지 않는다.

항목마다 관측 사실과 추정을 나누고 `합의 / 근거를 들어 기각 / 미합의 / 판단 불가`를 기록해 보고에 포함한다. 중요한 판단의 확정·기각에는 위 모델 구성에 따른 합의가 필요하다.

### 호출 시점과 재검토

- 정기 상태 조회 때마다 검토자를 호출하지 않는다. 호출 시점은 **새로 확정·기각하는 판단을 담은 감사 보고 전, 중요한 조치 확정 전, 완료·정리 배치 전**이다.
- 같은 자료를 쓰는 항목은 한 번에 묶되 항목별로 판정을 받는다. 이미 합의한 항목은 근거·요청·상태가 바뀐 것만 재검토한다. 실행 직전 상태 재확인은 총괄이 한다.

### 조치 전달과 확인

- 합의된 조치는 **소유 감독**에게 `send_agent_prompt`로 전달한다. 첫 요청에 근거·요구 조치·요청 식별자·완료 확인 기준과 최종 보고 수신자 `{serverId, agentId}`를 포함한다. 작업자에게 넘긴 경우에도 해당 조치의 최종 결과·검증 근거 또는 차단·필요 결정을 직접 보고하게 한다. 감독에게 보내는 모든 `send_agent_prompt`에는 `activeTurnBehavior: "steer"`와 `notifyOnFinish: true`를 명시하고, 가능하면 감독이 idle일 때 보낸다. 완료 알림으로 회신을 받아 기록하되 첫 턴의 진행 회신으로 항목을 닫지 않는다. 응답 불가는 위 절차로 후속 감독이 없음을 확인했거나, 최신 감독에게 전송한 뒤 그 감독의 다음 턴이 끝났는데도 회신이 없는 경우다. 진행 중인 작업자를 직접 재개·중단하거나 lane을 인수하지 않는다. 완료 후 archive는 아래 절차로만 수행한다. 응답 불가면 사용자에게 다음 결정을 요청한다. 사용자 승인이 필요한 조치는 합의만으로 실행하지 않는다.
- 사용자에게는 최종 보고와 필요한 결정 요청을 전한다. 내부 지적·반박·조율은 독립 검토자와 소유 감독 사이에서 처리한다. 조치 전달이나 응답 종료만으로 해결됐다고 보고하지 않고, 감독의 결과와 공유 기록·실제 상태를 대조해 닫는다.

## 완료 판정과 세션 정리

- 에이전트·workspace archive 모두 [yw-supervisor의 archive 전 공통 안전 대조](../yw-supervisor/SKILL.md#archive-전-공통-안전-대조)를 먼저 통과해야 한다. 아래 완료 판정·CLI 절차와 옛 감독 정리에도 같은 대조를 적용한다.
- 다른 감독 lane의 세션 detach는 소유 감독에게 요청해 그 감독이 실행·readback·보고 경로 갱신을 하게 한다. 사용자 승인이 있을 때만 총괄 감독이 직접 실행한다. 동의 주체는 위 공통 대조의 권한 내 분리 규칙을 따른다.
- 감독마다 **첫 사용자 목표와 이후의 모든 사용자 요청**(사용자 메시지와 감독 기록)을 완료 근거와 대조한다. 감독의 마지막 응답이 사용자 결정·답을 기다리고 있지 않은지도 확인한다. 공유 기록의 이슈 closed/merged 라벨·PR merged 상태, 하위 작업자·리뷰어의 실제 상태(running·백그라운드 대기 없음), 감독 기록의 대기 결정·미해결 조치가 없는지를 함께 확인한다. 사용자가 요청한 heartbeat/schedule이 남은 감독은 완료로 보지 않는다. PR 병합이나 감독의 idle 상태 하나만으로 완료를 판정하지 않는다.
- **heartbeat/schedule 확인:** schedule은 호스트별 `list_schedules`(원격은 `paseo schedule ls --json --host <검증한 endpoint>`)에서 `target.agentId`가 그 감독이나 소유 하위 에이전트인 활성 항목을 찾는다. heartbeat는 이 목록에 나오지 않고(Paseo 0.15.1에서 확인), 다른 에이전트의 heartbeat를 조회하는 MCP 도구도 없다. 감독 기록의 heartbeat 생성·삭제 기록에 남은 항목이 없거나, 소유 감독이 남은 heartbeat가 없다고 회신하면 부재 근거로 인정한다. 같은 호스트의 현재 데몬이 사용하는 heartbeat 저장소임을 확인한 경우, 전체 저장 항목을 읽고 감독·인계 체인·소유 하위의 대상 ID와 상태를 대조한 결과를 부재 근거로 인정한다. 확인 시각과 경로를 기록한다. 저장소 경로·완전성·읽기 성공을 확인할 수 없거나 원격 호스트이면 기존 기록·소유 감독 회신 기준을 적용한다. paused는 삭제·부재로 기록하지 않는다. 기록에 heartbeat 항목이 아예 없는 것은 없다는 근거가 아니다. 어느 근거도 없으면 확인 불가로 남기고 닫지 않는다.
- 판정은 `완료 / 미완료(남은 조치) / 판단 불가`로 나누고, 누적 사용자 요청·완료 근거의 출처·남은 조치와 판정 이유를 총괄 감독 기록에 남긴다. **위 "독립 검토와 조치"의 모델 구성·절차에 따라 완료 판정과 정리 대상을 합의한다.** 누적 사용자 요청·소유·실제 상태를 확인할 수 없으면 판단 불가로 남기고 닫지 않는다.
- 완료로 확인된 감독과 그 감독 소유로 확인된 하위 작업자·리뷰어 에이전트는 위 공통 대조의 에이전트 archive 경로로 닫는다. 리프부터 archive하고 매 호출 직전에 아직 archive되지 않은 후손이 0인지 조회·확인한다. 실행·백그라운드 대기와 미해결 조치가 새로 생기지 않았는지도 재확인하고, 대상 `{serverId, agentId}`와 결과를 기록한다. 현재 총괄 감독 자신은 정리 대상에서 제외한다. 실행 결과와 이미 archive된 응답은 공통 대조의 상태 변경 확인을 따르고, 그 밖의 거절은 보존·기록한다. 거절된 경우 그 에이전트가 있는 workspace도 남기며, 다음 완료 판정에서 다시 확인한다.
- **이어받은 뒤 남은 옛 감독:** 최신 감독이 위 기준으로 완료 판정되면, 그 감독에게 이어진 옛 closed 세션도 같은 정리 배치에서 재개하지 않고 위 정리 절차(호출 직전 closed 재확인, 거절 시 보존)로 닫는다. 체인은 "감독과 lane 발견"의 이어받은 작업자 절차로 끝까지 하나로 확인돼야 한다. 완료 판정의 누적 사용자 요청과 하위 에이전트 확인에는 체인의 모든 세션에서 받은 요청과 그 세션들을 부모로 둔 에이전트를 포함한다. 분기·순환이 있거나, 다른 호스트의 후속 여부를 공유 기록으로 확인할 수 없거나, 옛 세션이 error면 남긴다. 최신 감독이 미완료인 동안에는 옛 세션을 남긴다(누적 요청과 알림 중계의 근거로 필요할 수 있다).
- 해당 lane의 workspace는 **브랜치가 머지됐거나 PR이 닫혔고**, 위 공통 안전 대조를 모두 통과한 뒤에만 `archive_workspace`한다. 이때 자기 workspace는 총괄 감독 자신을 기준으로 대조한다. workspace 추가 조건을 통과하지 못하거나 공유 여부가 불명확하면 workspace는 남긴다. 개별 에이전트도 그 대상을 기준으로 공통 안전 대조를 통과하고 완료·소유가 확인된 경우에만 공통 대조의 에이전트 archive 경로로 닫는다. 어느 조건이든 확인할 수 없으면 남기고 이유를 기록한다.
- workspace는 로컬 MCP `archive_workspace`를 사용한다. 대상 호스트·정리 경로를 확인할 수 없으면 남기고 보고한다.
- 원격 workspace는 남긴다. 위 안전 대조의 미커밋 변경을 원격에서 확인할 수단이 없어 대조를 통과할 수 없기 때문이다. 원격 CLI `paseo workspace archive <workspace ID> --host <검증한 endpoint>`(MCP archive에는 `serverId`가 없다)는 그 확인 수단이 이 문서에 정해진 뒤에만 쓴다.
- 미완료 감독은 닫지 않고 남은 조치를 그 감독에게 전달한다. 감독이 응답할 수 없으면 사용자 보고에 올린다. 미커밋 변경이 있는 worktree, 소유를 판단할 수 없는 항목, stash, 원격 브랜치 삭제·PR 닫기는 사용자 승인 뒤에만 정리한다. 완료 후 에이전트·workspace archive 권한을 이런 추가 정리의 승인으로 확대하지 않는다.

## 보고와 인계

- 보고에는 **감독별 lane 상태 표**, 감사 지적(관측 사실/추정과 근거 출처), **정리한 것 / 남긴 것과 이유**, 취한 조치와 확인 결과, 사용자 결정이 필요한 항목을 포함한다. 매핑·상태를 확인하지 못한 범위도 밝힌다.
- 사용자 요청·재개·결과 알림 등 필요한 시점에 상태를 대조한다. 최종 결과를 기다리는 열린 조치의 대조용 heartbeat에는 `maxRuns` 또는 `expiresIn`을 지정한다. 열린 조치가 없어지면 삭제하고, 만료 시 남은 조치를 보고한다. 자동으로 무한 연장하지 않는다. ID·목적·해제 조건은 관리 기록에 남긴다. 무기한 감시·heartbeat/schedule은 사용자가 요청했을 때만 둔다.
- 인계는 [yw-supervisor의 "감독자 전체 인계"](../yw-supervisor/SKILL.md#감독자-전체-인계)를 따르되 범위는 **감사 대상 감독 목록과 lane 매핑, 미결 지적·합의 결과·대기 결정·다음 조치**다. 감사 대상 lane 자체의 소유권은 옮기지 않는다. 새 총괄 감독의 `{serverId, agentId}`와 보고 경로를 소유 감독에게 알리고, 별도로 배정한 자신의 작업이 있으면 그 작업도 빠짐없이 인계한다.
